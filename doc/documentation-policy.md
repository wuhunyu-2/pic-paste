# 文档持续维护约定

## 原则

`doc/` 是**受版本控制、随项目演进的权威工程资料**，不是初始化完成后永久不变的设计备忘录。新的事实与旧文档冲突时，Agent 不能只修改代码或 Issue 而不更新规范；也不能把变更直接写进 `AGENTS.md` 以绕过原有文档结构。

## 变更触发矩阵

| 实际变化 | 必须检查并更新的文档 |
| --- | --- |
| 新增、删除或改变用户行为 / 功能优先级 | `requirements.md`；重大取舍补充 ADR |
| 技术栈、模块边界、数据流、窗口、坐标模型变化 | `architecture.md` + 新的 ADR；更新受影响的 plan |
| 开发命令、Xcode/Swift 版本、依赖、提交工作流变化 | `development.md`，相关 README/plan |
| CI 门槛、设备矩阵、交付证据或实测方法变化 | `acceptance.md`，受影响的 PR 模板 |
| Logo、图标、色彩、设计资源变化 | `branding.md` 与 `assets/logo/` |
| 文档移动、更名、新增或废弃 | `doc/README.md`；入口改变时更新 `AGENTS.md`、`README.md` |
| Bug 修复揭示原先的架构假设或设计限制错误 | 相应长期文档；必要时 ADR |
| 仅 Issue 的状态、负责人、阻塞、CI 链接或完成百分比变化 | **只更新 GitHub Issue**，不复制到文档 |

## Agent 在每个 PR 的动作

1. 开始前阅读目标 Issue + 相关长期文档，确认当前版本，而不是机械执行过时计划。
2. 发现设计与代码事实不一致时，先在 Issue / PR 解释冲突；明确选择后同步修改适当文档。
3. 提交前审查修改清单是否涉及上表触发器；需要文档变化时和代码一起提交，并检查链接和示例命令仍有效。
4. PR 正文写明 **文档同步：已更新哪些文件 / 无需更新的理由**。文档变更不能只停留在 Issue 评论。
5. 验收后仅更新 Issue 勾选和证据；永不将瞬时“进度”反向复制到 `AGENTS.md`、`README.md` 或长期规范。

## ADR 维护

已采纳的 ADR 是决策历史。若结论被推翻，新增一个注明取代关系的 ADR，并更新现行架构/需求；不要直接改写旧 ADR 的历史背景来掩盖变更。小的实现或命令调整不需要为形式而新增 ADR。

## 文档质量

优先修改既有文档，不为同一主题创建重复说明。删除失效路径和过时命令；保持索引有效。真实设备结论必须有可追溯证据，未知状态明确标注未知，不以 CI 成功填补证据缺口。
